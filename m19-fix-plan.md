## Cycle correlation: `pipelineRunId` (NEW)

Each workflow run gets its own `runId`. A full cycle (investigate → spec → implement → QA → review → approve → merge → retro) spans multiple runIds, all keyed off one issue. To correlate score data and lookup history per-cycle, introduce **`pipelineRunId`**:

- **Generated:** at spec-author execution (M19.17 owns it). UUID.
- **Scope:** **per PR lifecycle**, not per attempt. QA-failed → fix-feedback → re-QA REUSES the same `pipelineRunId`. The PR (and its worktree) persists across retries; the score covers the cumulative cycle.
- **Optional `attemptId`:** UUID per retry within the PR lifecycle. Increments when fix-feedback or QA re-runs. Use for per-attempt event grouping; pipelineRunId stays stable.
- **New `pipelineRunId`:** only when a brand new PR opens for the same issue (e.g. PR closed without merge, then re-opened or replaced).
- **Carried:** on every event payload throughout the cycle (`agent.run-started`, `pr.opened`, `qa.completed`, `review.completed`, `merge-decision.completed`, retro events).
- **Stored:** as column on `engineering_specs`, `pr.opened` payload, `run_quality_scores`. Key for cross-stage lookups.

Used by:
- M19.17: **owns generation** — spec-author workflow generates pipelineRunId, persists alongside spec.
- M19.18: parallel-implement reads pipelineRunId from spec, propagates to `pr.opened` payload.
- M19.19: deterministic verify reads pipelineRunId from cycle context, tags tier events.
- M19.21: merge-decision (inside approve action) reads cycle events by pipelineRunId, builds RunArtifacts, computes score.
- M19.21: `run_quality_scores` keyed by pipelineRunId. Convergence query reads prior pipelineRunIds for same projectId.
