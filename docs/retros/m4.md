# M4 Retrospective — Controlled Claude CLI Runtime Spike

**Closed:** 2026-05-02
**Issues shipped:** 13 (M4.01–M4.12 + #78 subprocess security rules)
**PRs merged:** 3 (M4.01, M4.02–M4.12 combined, M4.78)

## What worked

Shipping M4.02–M4.12 as a single PR was the right call. The entire agent runtime, tool layer,
skills, CLI command, and UI integration are tightly coupled — splitting them into 11 separate
PRs would have required each to land in dependency order with no parallelism. The combined PR
landed cleanly in one session with all tests green.

The subprocess security model (argv array, absolute binary resolution, minimal env, stdout cap,
30 s timeout) was well-specified in issue #78 before implementation began. Having the rules
written first meant the implementation was mechanical — no design decisions at coding time.
The unit tests for each rule are precise and fast.

The holdout enforcement test (`echo-test-holdout`) is a clean pattern. Using a second skill
variant with `requiresFreshContext: true` to prove the type system enforces holdout constraints
at compile time — not just runtime — is reusable for every future holdout skill.

Dry-run mode (`--dry-run`) in `run-agent` proved immediately useful for the exit audit:
it validates AgentSpec assembly without consuming any API budget or requiring Claude CLI.

## What didn't work

**M4.78 broke CI on main.** The subprocess security test PR introduced `as any` casts that
Biome's `noExplicitAny` rule rejects. The fix was in the branch as unstaged changes but was
never committed before the PR merged. Same pattern as M3: a PR merged with a red CI run.

**`.worktrees/` not excluded from biome.json.** Biome checked worktree copies of every file,
inflating lint scope and occasionally surfacing errors in files that were correct in the
main tree. Fixed in the exit audit.

**No ADRs at time of implementation.** Two major new `core/` modules (agent-runtime, tool-layer)
shipped with no ADRs. The decisions were recoverable from code reading but took time during
the exit audit. The audit itself became the ADR-writing session.

**`fresh-context.ts` named `context-assembly.ts` without updating PLAN.md.** Minor, but it
created a discrepancy that caused confusion during the audit. PLAN.md section 6 was a stale
reference for anyone reading it.

**`goose run-agent` end-to-end not fully verified.** The exit criterion requires a live run
with decision-summary events visible in the Timeline UI. This wasn't verified before the
milestone was marked structurally complete — it requires human verification with a real
Claude CLI spawn (can't be automated from within Claude Code due to nested-invocation guards).

## What to change for M5

1. **Never merge a PR that fails lint.** The M3 retro said this. M4 repeated it. Enforcement
   needs to be structural: add a branch protection rule requiring CI green before merge, or
   at minimum run `pnpm lint` locally and confirm green before pushing.

2. **Write ADRs at implementation time, not in the exit audit.** When a PR introduces a new
   `core/` module or makes a non-obvious architectural decision, the ADR goes in the same PR.
   The exit audit should verify ADRs exist — not write them.

3. **Update PLAN.md section 6 in the same PR that diverges from it.** If implementation
   picks a different name or structure, update the plan tree in the same commit. Don't leave
   stale references for the next reader.

4. **Add `.worktrees/` to biome ignore at the start of a milestone, not the end.**
   This is now fixed in biome.json; it should stay excluded for all future milestones.

5. **Verify the headline exit criterion manually before closing the milestone.** For M5 this
   means: triage runs, labels appear, repo candidate is attached. A dry-run or unit test is
   not sufficient — the real GitHub webhook flow must be demonstrated once.
