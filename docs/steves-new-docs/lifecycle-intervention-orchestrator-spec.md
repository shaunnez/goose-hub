# Dark Factory Lifecycle Intervention And Orchestrator Spec

Status: draft for implementation
Date: 2026-04-25
Owner surface: Dark Factory command center

## 1. Purpose

Dark Factory should be able to run a feature, bug fix, roadmap slice, or third-party intake item from request to shipped evidence through the UI and orchestrator, without requiring the operator to drop into a terminal.

The current system has strong bones: lifecycle state, gates, work packages, terminal sessions, feed rows, roadmap intake, LLM decision briefs, and dev-persona auto-fix loops. The failure is coordination. Multiple surfaces describe work, but no durable control-plane object owns an operator/orchestrator intervention from detection through decision, action, verification, and resolution.

This spec defines that control plane.

## 2. Non-Negotiable Product Outcomes

1. The operator can understand what is happening across many teams from one command center.
2. Every decision card is generated by the orchestrator or deterministic state, not invented by the frontend.
3. A decision is durable. After it is made, the same issue cannot immediately reappear unless verification fails with new evidence.
4. The orchestrator can operate in manual mode or autopilot mode.
5. The factory can log its own bugs, split them into lifecycles, route them through the roadmap/backlog, fix them, verify them, and close them.
6. Third-party intake can become triaged roadmap work or autonomous bug-fix work under policy.
7. The three views remain distinct:
   - Strategic: portfolio, roadmap, risk, throughput.
   - Operator: current work, decisions, team summaries, intervention queue.
   - Tactical: exact lifecycle status, gates, sessions, work packages, harness evidence.

## 4. Diagnosis

The current bug is architectural, not cosmetic.

Feed rows are being used as current control state. They are an audit stream. They cannot reliably represent whether an escalation is open, decided, being applied, verifying, resolved, or reopened.

The lifecycle phase is also not enough. `ESCALATED`, `FIX_LOOP`, `BLOCKED`, and reset gates describe work condition, but not the operator/orchestrator control loop around that condition.

The system currently has fragmented sources of truth:

- lifecycle `phase`
- lifecycle `escalation_reason`
- gates
- work packages
- terminal/session status
- `activity_log.needs_human`
- orchestrator decisions/messages
- operator decision rows
- frontend dedupe state

This causes duplicate escalations, stale `escalation_reason`, stale row phases, inflated `needs_human` counts, inconsistent tactical/operator views, and decisions that clear a UI card without changing the real lifecycle condition.

## 5. New Core Object: Lifecycle Intervention

Introduce a first-class durable object: `lifecycle_interventions`.

An intervention is the source of truth for a detected condition that needs orchestration, operator judgment, autopilot action, verification, or closure.

The feed becomes a projection of interventions and work updates. It is not authoritative.

### 5.1 Intervention States

```text
OPEN
PROPOSED
DECIDED
APPLYING
VERIFYING
RESOLVED
REOPENED
ABORTED
SUPERSEDED
```

### 5.2 State Meaning

`OPEN`: monitor, orchestrator, agent, third-party intake, or self-dogfood loop found a condition.

`PROPOSED`: orchestrator generated a structured read and options.

`DECIDED`: operator or autopilot selected an option.

`APPLYING`: system is executing the selected action: spawn, kill, resume, nudge, reset, queue, split, harness, rollback, etc.

`VERIFYING`: action completed and the factory is waiting for evidence.

`RESOLVED`: verification passed or operator intentionally closed.

`REOPENED`: verification failed or the same root issue recurred with materially new evidence.

`ABORTED`: operator/autopilot deliberately stopped the intervention.

`SUPERSEDED`: replaced by a more current intervention, roadmap item, or parent lifecycle.

### 5.3 Proposed Table

Add to `_SCHEMA_SQL` and mirror async migrations.

```sql
CREATE TABLE IF NOT EXISTS lifecycle_interventions (
    id TEXT PRIMARY KEY,
    feature TEXT,
    repo_name TEXT,
    parent_intervention_id TEXT,
    parent_lifecycle_feature TEXT,
    source TEXT NOT NULL,
    source_activity_log_id TEXT,
    source_db_commit_seq BIGINT,
    source_external_id TEXT,
    intervention_type TEXT NOT NULL,
    status TEXT NOT NULL,
    severity TEXT NOT NULL DEFAULT 'warning',
    dedupe_key TEXT NOT NULL,
    root_cause_signature TEXT NOT NULL,
    phase TEXT,
    iteration INTEGER,
    title TEXT NOT NULL,
    issue_summary TEXT NOT NULL,
    evidence_json TEXT NOT NULL DEFAULT '[]',
    missing_info_json TEXT NOT NULL DEFAULT '[]',
    options_json TEXT NOT NULL DEFAULT '[]',
    recommended_option_id TEXT,
    selected_option_id TEXT,
    selected_by TEXT,
    selected_mode TEXT,
    selected_note TEXT,
    action_payload_json TEXT NOT NULL DEFAULT '{}',
    application_result_json TEXT NOT NULL DEFAULT '{}',
    verification_plan_json TEXT NOT NULL DEFAULT '{}',
    verification_result_json TEXT NOT NULL DEFAULT '{}',
    generated_by_model TEXT,
    reasoning_trace_id TEXT,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,

```

### 5.4 Required Indexes

```sql
CREATE INDEX IF NOT EXISTS idx_lifecycle_interventions_feature_status
    ON lifecycle_interventions(feature, status, created_at DESC);

CREATE INDEX IF NOT EXISTS idx_lifecycle_interventions_status_created
    ON lifecycle_interventions(status, created_at DESC);

CREATE INDEX IF NOT EXISTS idx_lifecycle_interventions_dedupe
    ON lifecycle_interventions(dedupe_key);

CREATE INDEX IF NOT EXISTS idx_lifecycle_interventions_root_cause
    ON lifecycle_interventions(root_cause_signature);

CREATE INDEX IF NOT EXISTS idx_lifecycle_interventions_source_activity
    ON lifecycle_interventions(source_activity_log_id);
```

Defer unique constraints until duplicate historical data is measured. The service layer should still treat `(feature, root_cause_signature, status in open states)` as unique.

## 6. Core Reducer Contract

Add `dark_factory/lifecycle/interventions.py`.

This module owns intervention state transitions and side effects. Routes, daemon loops, feed decisions, roadmap intake, and orchestrator tools should call this service instead of each mutating their own idea of the world.

### 6.1 Public Methods

```python
open_or_update(candidate) -> InterventionRecord
attach_orchestrator_proposal(intervention_id, decision) -> InterventionRecord
decide(intervention_id, selected_option_id, selected_by, note, mode) -> InterventionRecord
apply(intervention_id) -> InterventionActionResult
mark_verifying(intervention_id, verification_plan) -> InterventionRecord
verify(intervention_id, verification_result) -> InterventionRecord
resolve(intervention_id, resolution) -> InterventionRecord
reopen(intervention_id, evidence_delta) -> InterventionRecord
abort(intervention_id, reason) -> InterventionRecord
supersede(intervention_id, replacement_id, reason) -> InterventionRecord
```

### 6.2 Reducer Invariants

1. All transitions are idempotent.
2. Applying the same decision twice returns the existing result.
3. A monitor tick updates an existing open/proposed/decided/applying/verifying intervention instead of opening a new one.
4. `RESOLVED` can only reopen if the new evidence has a different mutation digest or verification failure.
5. A lifecycle phase move out of `ESCALATED` must either resolve, supersede, or move the intervention to `VERIFYING`.
6. Direct lifecycle mutation must use existing gate and phase APIs.
7. The reducer writes activity-log projections, but activity-log writes are never the source of truth.

## 7. Orchestrator Structured Decision

The existing `propose_operator_decision` tool is the right direction. It must become canonical.

### 7.1 Canonical Schema

```python
class DecisionTarget(BaseModel):
    feature: str | None = None
    phase: str | None = None
    gate_name: str | None = None
    session_id: str | None = None
    work_package_id: str | None = None
    team_name: str | None = None
    roadmap_item_id: str | None = None
    external_ticket_id: str | None = None
    repo_name: str | None = None

class DecisionEvidence(BaseModel):
    source: Literal[
        "lifecycle", "gate", "work_package", "session", "feed",
        "tool", "operator_memory", "decision_history", "third_party",
        "dogfood", "harness", "roadmap"
    ]
    ref_id: str | None = None
    summary: str
    path_or_url: str | None = None

class DecisionOption(BaseModel):
    id: str
    label: str
    action_type: Literal[
        "approve", "reject", "defer", "escalate", "nudge", "kill",
        "resume", "spawn", "run_harness", "send_back", "complete",
        "split_lifecycle", "queue_roadmap", "create_bug", "autofix",
        "custom"
    ]
    target: DecisionTarget
    description: str
    why: str | None = None
    risk: str | None = None
    unblocks: str | None = None
    payload: dict = {}
    destructive: bool = False
    requires_reason: bool = False

class OrchestratorStructuredDecision(BaseModel):
    schema_version: Literal["orchestrator_decision.v1"]
    decision_type: Literal[
        "operator_brief", "gate_decision", "team_staffing",
        "session_recovery", "completion_decision", "harness_decision",
        "queue_priority", "scope_decision", "escalation",
        "autonomous_action", "roadmap_split", "third_party_intake",
        "self_bug"
    ]
    title: str
    target: DecisionTarget
    my_read: str
    decision_needed: str | None = None
    recommended_option_id: str | None = None
    options: list[DecisionOption]
    evidence: list[DecisionEvidence]
    missing_info: list[str] = []
    risk_level: Literal["low", "medium", "high", "critical"]
    confidence: float
    requires_human: bool
    autopilot_allowed: bool
    expected_outcome: str | None = None
    verification_required: bool = True
    trace_id: str | None = None
```

### 7.2 Decision Rules

Manual mode:

- Orchestrator proposes.
- Operator selects option or writes override.
- System applies selected option.

Autopilot mode:

- Orchestrator may select low/medium risk options within policy.
- Destructive actions require explicit policy allowance.
- Security, billing, data deletion, third-party outbound messages, production deploys, and broad refactors require human approval unless explicitly whitelisted.
- Every autopilot decision must leave an intervention audit trail with evidence and verification.

## 8. Monitor And Daemon Redesign

### 8.1 Monitor Output

`detect_escalations()` should return escalation candidates, not imply a new feed row.

Candidate fields:

```python
feature
phase
iteration
rule_id
severity
reason
recommendation
evidence
root_cause_signature
dedupe_key
verification_hint
```

### 8.2 Daemon Flow

Current:

```text
detect escalation -> maybe auto resolve -> mirror feed row -> ask orchestrator
```

New:

```text
detect candidate
-> intervention_service.open_or_update(candidate)
-> if needs proposal: orchestrator generates structured decision
-> intervention_service.attach_orchestrator_proposal(...)
-> if autopilot allowed: intervention_service.decide(..., mode="autopilot")
-> intervention_service.apply(...)
-> intervention_service.mark_verifying(...)
-> monitor verifies and resolves or reopens
```

### 8.3 Duplicate Prevention

The daemon must not use in-memory cooldown as the main dedupe mechanism.

Durable dedupe key examples:

```text
feature:phase:rule_id:gate_name
feature:iteration:failed_harness_layer_set_hash
feature:session_id:terminal_status
external:jira:ticket_id:updated_at_digest
dogfood:finding_fingerprint
```

## 10. Feed And UI Projection

### 10.1 Operator View

The operator view should be the current command queue:

- decisions
- active work updates
- verification updates
- blocked/stalled teams
- resolved items collapsed

It should not be a raw transcript.

Cards start collapsed and are ordered by time, not grouped by type.

Filters:

- `All`
- `Decisions`
- `Active work`
- `Verification`
- `Failures`
- `Resolved`
- search by feature/session/gate/WP/external ticket

### 10.2 Tactical View

Tactical view shows exact state for one feature:

- lifecycle phase
- intervention state
- work packages
- active/completed/failed sessions
- gates
- harness evidence
- last orchestrator decision
- next legal actions

The left menu must use the same current lifecycle/intervention source as the operator queue.

### 10.3 Strategic View

Strategic view shows:

- roadmap lanes
- blocked portfolio
- autopilot/manual mix
- throughput
- risk concentration
- aging interventions
- third-party intake health
- self-filed bug trends

Mission board and strategic roadmap should not duplicate each other. Strategic owns portfolio; operator owns current action.

## 11. Roadmap And Ask Decomposition

The system must support asks that are too large for one lifecycle.

### 11.1 New Orchestrator Tool

```python
propose_roadmap_split(
    ask: str,
    desired_outcome: str,
    constraints: list[str],
    available_context: list[DecisionEvidence],
) -> RoadmapSplit
```

### 11.2 RoadmapSplit Schema

```python
class RoadmapSplitItem(BaseModel):
    feature_name: str
    description: str
    priority: Literal["P0", "P1", "P2", "P3"]
    mode: Literal["gated", "autonomous"]
    dependency_ids: list[str]
    suggested_workflow: str
    acceptance_criteria: list[str]
    harness_requirements: list[str]
    risk_level: Literal["low", "medium", "high", "critical"]
    autopilot_allowed: bool

class RoadmapSplit(BaseModel):
    parent_ask_id: str
    title: str
    summary: str
    items: list[RoadmapSplitItem]
    recommended_execution_order: list[list[str]]
    requires_operator_approval: bool
```

### 11.3 Execution

- Small asks become one lifecycle.
- Large asks become a parent roadmap item plus child lifecycles.
- Parallelizable children are queued in the same dependency level.
- The operator can approve the whole split or edit child items.
- Autopilot can approve low-risk splits only when policy allows.

Existing `/api/factory/roadmap` should remain the compatibility route. A richer route can be added:

```text
POST /api/factory/roadmap/split
POST /api/factory/roadmap/{id}/approve
POST /api/factory/roadmap/{id}/dispatch
```

## 12. Self-Logged Bugs And Auto-Completion

Dark Factory should file and fix its own bugs.

Sources:

- dev-persona loop findings
- Playwright dogfood failures
- API consistency checks
- daemon exceptions
- stale lifecycle/intervention detectors
- user feedback
- third-party bug reports
- harness regressions

### 12.1 Self-Bug Flow

```text
finding detected
-> classify: real_bug | capability_gap | noise
-> dedupe by fingerprint
-> if real_bug high confidence: create bug lifecycle or autofix intervention
-> if capability_gap or low confidence: create roadmap/spec item
-> assign workflow: hotfix_lifecycle | feature_lifecycle | investigation_swarm
-> build/fix
-> run harness
-> verify no recurrence
-> mark bug lifecycle completed
-> resolve source intervention/finding
```

### 12.2 New Self-Bug Record

This may be a table or a typed lifecycle intervention type.

Preferred: use `lifecycle_interventions` with:

```text
intervention_type = self_bug
source = dogfood | harness | daemon_exception | user_feedback | third_party
source_external_id = finding fingerprint or ticket id
root_cause_signature = stable bug fingerprint
```

Only create a separate `factory_bugs` table if product reporting needs bug-specific lifecycle beyond interventions.

### 12.3 Completion Criteria

A self-filed bug can auto-complete only when:

1. The linked lifecycle reaches `COMPLETED` or equivalent.
2. Required harnesses pass.
3. The original finding fingerprint is not reproduced.
4. The fix changed at least one meaningful file or intentionally marked no-op with evidence.
5. Any generated spec/backlog item is linked.
6. The intervention is moved to `RESOLVED` with verification evidence.

```text

-> classify
```

### 13.3 Third-Party Safety

Autopilot may ingest and fix. It should not externally comment, close, assign, merge, or deploy unless explicitly allowed by policy.

Outbound third-party actions are their own interventions with evidence and approval policy.

## 15. Harness Requirements

Minimum backend tests:

1. Opening same candidate repeatedly updates one intervention.
2. Daemon restart does not reopen decided/verifying intervention.
3. `ESCALATED -> FIX_LOOP` clears or archives stale escalation context.
4. Feed decision transitions intervention and executes action.
5. Failed verification reopens same intervention.
6. Resolved intervention stays collapsed unless new evidence arrives.
7. Autopilot can decide only policy-allowed options.
8. Broad ask splits into multiple roadmap items with dependencies.
9. Dev-persona finding creates self-bug or roadmap item.
10. Self-bug auto-completes only with verification.

Minimum frontend tests:

1. Operator queue renders intervention decision card.
2. Decision card starts collapsed.
3. Selecting option posts durable intervention decision.
4. Decided card collapses to issue + decision + clear.
5. Tactical view reflects same intervention status.
6. Strategic view counts active/resolved interventions correctly.
7. Search/filter by decision/update/verification works.
8. Roadmap split review renders parent/child dependencies.

Minimum dogfood tests:

1. Use the UI to disposition `df-daemon-asyncpg-migration`.
2. Use the UI to disposition `df-operator-hud-redesign-2026-04-22`.
3. Run a synthetic self-bug through detection, fix, harness, and auto-close.
4. Run a broad ask through roadmap split, parallel lifecycles, verification, and parent completion.

## 16. Definition Of Done

This project is done when:

1. The current stuck features can be advanced or deliberately killed/deferred through UI intervention cards.
2. The same issue does not duplicate across feed, tactical, and operator views.
3. Orchestrator decisions are structured, useful, and executable.
4. Autopilot/manual mode materially changes behavior.
5. The factory can create its own bug lifecycle from a dogfood finding.
6. The factory can split a broad ask into multiple roadmap/lifecycle items.
7. Verification evidence, not optimistic text, closes work.
8. A senior engineer can manage delivery without terminal access for normal operations.

## 17. First Implementation Slice

The first shippable slice should be narrow:

1. Add intervention table and models.
2. Add reducer with `open_or_update`, `attach_proposal`, `decide`, `resolve`.
3. Route daemon escalation candidates into interventions.
4. Make `/feed/{entry_id}/decide` update intervention state.
5. Project active interventions into operator queue.
6. Add duplicate/restart/decision tests.
7. Dogfood the two stuck features.

Do not start third-party intake until this slice is stable.

Do not start broad roadmap split automation until intervention state is durable.

Do not expand UI polish until one stuck feature can be dispositioned cleanly end to end.
